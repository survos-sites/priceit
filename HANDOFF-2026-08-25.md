## What broke today, and why (so it is not re-diagnosed)

Every one of these was invisible locally and only appeared on the server.

1. **Assets all 404'd.** `asset-map:compile` never ran. It belongs in
   `app.json`'s `predeploy`, which is where ssai does it; priceit had no
   `app.json` at all.

2. **`Unrecognized option "favicon"` / `"apps"`.** `vendor/survos/*` is
   symlinked to mono, so config using unreleased bundle features works locally
   and fails on a server installing from Packagist. Hit twice: tabler-bundle
   (needed ≥2.24.0) and quickbase-bundle (needed 2.24.34, released mid-session).
   `"survos/quickbase-bundle": "*"` was the underlying sin — it pinned nothing.

3. **`pwa.image_processor.gd` does not exist.** The build image had no GD, so
   pwa-bundle skipped registering it and `pwa:compile` died. Fixed by declaring
   `ext-gd`, `ext-intl`, `ext-pdo_pgsql` in composer.json.

4. **403 on everything.** With no `Procfile` the buildpack serves the project
   root. The deploy reported success and answered 403 to every request.

5. **500 on upload** — schema drift: `Item` gained
   `quickbase_inventory_record_id` and prod had never heard of it.

6. **413 on upload** — three separate limits, all of which must agree. Written
   up in `mono/bu/deployment-bundle/docs/uploads-and-limits.md`.

7. **`Syntax error for https://laptop-depot.../api/print-jobs`** — depot
   answered a failed print with 502, and Cloudflare replaces 5xx bodies with its
   own plain-text page, destroying the JSON that said *why*. Now 422.

## Known gaps

- **Migrations cannot run in production.** They are SQLite-shaped
  (`CREATE TEMPORARY TABLE __temp__item`) because dev is SQLite and prod is
  Postgres. `predeploy` runs `doctrine:schema:update --force --complete` as a
  stopgap. The real fix is moving dev to the shared Docker Postgres per
  CONVENTIONS, then regenerating migrations.
- **`dokku nginx:set priceit client-max-body-size 100m` is server state.**
  Nothing in the repo records it. Rebuild the host and uploads break at 1M with
  no diff to explain it. `nginx.conf.sigil` is the repo-tracked fix.
- **No error tracking.** GlitchTip is specced in survos/docker#8.
- **`quickbaseInventoryRecordId`** is on `Item` from another session's work. It
  is Quickbase's surrogate key and should stay a foreign key — the accession
  number should be ours.

## Next: generalising to "catalog-it"

Discussed, not started. The Lion's Club loan closet wants an inventory of
medical equipment — wheelchairs, walkers, shower seats, Hoyer lifts. Design
notes from the conversation:

- **Identifiers should be opaque** (`2026.LLC.001`), not type-derived
  (`WhlChr1`). Reclassification — "motorized wheelchair is its own category" —
  is exactly what breaks an ID with type baked in. Type belongs on the printed
  label, not in the key.
- **"Multi-photo" is really "photos with roles"**: item, serial/registration
  plate, accessory, condition detail. Each role wants its own prompt — reading a
  serial plate is a different task from describing a chair. ssai already models
  this: `IntakeProfile` with `imageRoles`, each carrying an `AiTaskPlan`. The
  single/double/multi dropdown should become "pick a profile".
- **Multi-part items** (motorized chair + charger): one accession with a
  components list, since what matters is what goes out and comes back together.
  Promote a component to its own item only if it can be lent separately.
- **Lending is a separate system** from cataloguing. Who has it, when it is due
  — keep that out of the catalog model.

Tac was to supply photos of actual loan-closet equipment; a brief for analysing
them was drafted but the photos had not arrived. **This waits until after the
auction.**

## Commands

```bash
bin/console auction:pull                 # (ddys, not this app)
bin/console item:suggest <id>            # re-run the AI on one item
bin/console item:suggest --pending       # anything still at `new` or `failed`
bin/console label:preview <id>           # ZPL to stdout
bin/console label:print <id>             # build and push to depot
bin/console doc:workflows                # regenerate docs/workflow/item.md
```

Locally the worker runs from `.symfony.local.yaml`; if items sit at `new`,
check `pgrep -af "messenger:consume"`.
